# Care: CL Apps suite alignment

Local release preparation, 9 November 2026. No deployment or customer communication has been performed.

Care remains the existing independent repair/aftercare app. Do not replace its registration or database. Its service catalogue, cases, quotes, customer approval, progress, billing and email records remain in the existing codebase.

The merchant workspace now shares the newer CL Apps header, typographic mark, navigation, colours, typography, cards and controls. Existing merchant-controlled customer logos and colours are retained. A configured home page shows recent cases instead of repeating completed onboarding.

One nullable `MerchantProfile.automaticEmail` field is added. New profiles explicitly set false. Existing null values retain the previous customer-email behaviour, and merchants can review/change the setting in Branding & setup. Demo creation never sends email. No existing subscription price, plan identity, usage value or customer token changes.

Public customer responses now filter internal updates and merchant billing fields before serialisation. Customer-submitted Shopify references are reverified rather than trusted from hidden fields. Photo inputs are bounded to supported formats and size. Quote approval checks the exact quote the customer saw and rejects a stale amount. These checks do not introduce payment collection; Care still records estimates and approvals only.

The Dockerfile generates its own Prisma client during the build instead of depending on a developer's existing generated client. Runtime files are owned by the non-root Node user so the established `docker-start` setup can generate/apply the additive schema safely.

## Existing installation deployment

1. Back up and inspect the current Care database. Preserve its current environment, registration, domain and provider configuration.
2. Review the additive nullable-column schema diff. The current `npm run setup` still uses `prisma db push` without an accept-data-loss flag, matching the existing deployment workflow. Do not approve destructive changes if an unexpected drift warning appears.
3. Deploy the reviewed Care source using its existing service and the updated Dockerfile. Verify an existing merchant retains branding, case history, plan and allowance. A new merchant must show customer email off. Do not send real customer notifications as a release test.
4. Check the refreshed home, cases, catalogue, branding, billing and customer tracking page. Keep the previous code release for rollback; retain the additive column if rolling back code.

The supplied migrations contain a pre-change baseline and the single column addition. They work for a fresh database. To adopt migrations for an existing database previously managed with `db push`, first verify the schema and mark the baseline applied; never run the baseline's create-table SQL against populated tables. Migration adoption is separate from this visual release.

Local preview support is guarded by `CARE_LOCAL_PREVIEW` and refuses production mode, external databases and external credentials. The preview is not an authentication path available in production. Start it from the sibling standalone-apps package with `npm run preview:care`.

The complete suite release instructions and recorded test evidence are in `../standalone-apps/README.md` and its final validation record. Production installation, billing and provider checks still require the real existing service; local tests are not a claim that those external checks have been completed.
